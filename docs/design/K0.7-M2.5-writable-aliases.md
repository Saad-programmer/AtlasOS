# K0.7-M2.5 — Alias inscriptibles (E3) : audit et conception

**Statut :** M2.5a, audit et conception. **Aucun changement de politique de projection.** E3 reste ouvert.
**Base auditée :** commit `e619b7f`, image de production `build/samos.elf`, QEMU 8.2.2, `-m 128M`.

## 1. Rappel du défaut

En K0.6 (`docs/review/evidence/k06-memory-defects.txt`, E3), `vmm_map(0xD0000000, page de .text, PTE_WRITE)` était accepté, et une écriture par cet alias modifiait le code de `kmain` (`53e58955 -> cccccccc`). En `e619b7f`, ce chemin existe toujours : `map_page()` ne compte pas les cadres non `ALLOCATED`, mais il ne les refuse pas non plus.

## 2. Carte des régions physiques (image de production)

Valeurs lues avec `nm build/samos.elf`. L'image de test a la même structure, à des adresses différentes, car son code est plus volumineux.

| Région | Début | Fin (exclue) | Contenu | Doit être modifiable ? |
|---|---|---|---|---|
| mémoire basse | `0x00001000` | `0x00100000` | BIOS, EBDA, VGA `0xB8000` | VGA seulement |
| `.text` | `0x00100000` | `0x00105251` (page `0x106000`) | code du noyau | **non** |
| `.rodata` | `0x00106000` | `0x00107470` (page `0x108000`) | constantes | **non** |
| `.data` | `0x00108000` | `0x00108008` | données initialisées | oui |
| `.bss` | `0x00109000` | `0x0018ba80` | `g_gdt` (`0x109000`), `g_tss_main` (`0x109030`), `g_tss_df` (`0x1090a0`), `g_df_stack` (`0x109110`), `g_idt` (`0x10a110`), `g_handlers` (`0x10a918`), `g_meta` (`0x10ba80`, table du PMM, 512 KiB) | oui (voir 4.3) |
| page de garde | `0x0018c000` | `0x0018d000` | aucune | jamais projetée |
| pile de démarrage | `0x0018d000` | `0x00191000` | pile | oui |
| RAM gérée | `0x00191000` | `0x07fe0000` | répertoire de pages (CR3 = `0x00191000`), tables de pages, cadres libres et alloués | voir 4.4 |

Tous ces cadres de l'image (`0x100000`-`0x191000`) ont le type `FRAME_KERNEL`. **Le type ne distingue pas** le code, les constantes et les données modifiables : la distinction n'existe que dans les symboles du linker et dans les droits de l'identité.

## 3. Droits réellement installés (observation indépendante)

Les droits ont été lus par le moniteur QEMU (`info mem`), qui parcourt les tables du processeur émulé sans passer par le code du noyau. CR0 = `0x80010011` (PG, WP, ET, PE).

```text
0000000000001000-0000000000100000 00000000000ff000 -rw
0000000000100000-0000000000108000 0000000000008000 -r-
0000000000108000-000000000018c000 0000000000084000 -rw
000000000018d000-0000000007fe0000 0000000007e53000 -rw
```

Toutes les pages sont en mode superviseur (colonne U à `-`). `.text` et `.rodata` sont en lecture seule, et CR0.WP rend cette lecture seule effective pour le ring 0 (démontré en K0.6 par `pf_write_text`).

## 4. Analyse par catégorie

### 4.1 Code (`.text`) et constantes (`.rodata`)

- **Dans l'identité :** lecture seule, effective. Aucun alias inscriptible existant.
- **Dans une projection dynamique :** un alias inscriptible peut être créé par `vmm_map(..., PTE_WRITE)`. C'est E3.
- **Conclusion :** refuser les nouveaux alias inscriptibles **suffit** pour ces deux régions, à condition que les tables de pages, elles, ne soient pas modifiables par un autre chemin (4.4).

### 4.2 Données modifiables du noyau (`.data`, `.bss`, pile)

Ces données sont déjà inscriptibles dans l'identité. Un alias dynamique n'ajoute aucun droit d'écriture, mais il élargit la surface (une seconde adresse pour la GDT, l'IDT, la table des gestionnaires, la table du PMM). **Aucun besoin légitime en K0** : aucun appelant ne projette de données du noyau dynamiquement.

### 4.3 Structures critiques dans `.bss`

La GDT, les TSS, l'IDT, la table des gestionnaires et la table des descripteurs du PMM sont des cadres `FRAME_KERNEL` inscriptibles dans l'identité.

- La GDT et les TSS **doivent** rester inscriptibles : le CPU écrit le bit « occupé » du TSS lors d'une commutation de tâche matérielle (porte de double faute).
- L'IDT et la table des gestionnaires pourraient passer en lecture seule après l'initialisation. C'est une mesure de durcissement distincte, hors du périmètre de E3 : elle est notée dans les suites possibles.

### 4.4 Tables de pages : **le refus de nouveaux alias ne suffit pas**

Le répertoire (CR3 = `0x00191000`) et les tables de pages sont alloués dans la RAM gérée. Ils possèdent **déjà un alias inscriptible : l'identité** (plage `0x18d000`-`0x7fe0000` en `-rw`). C'est voulu, car le VMM actuel modifie les tables par leur adresse physique.

Conséquence : une écriture du noyau à l'adresse d'une table de pages peut changer n'importe quelle PTE, par exemple passer la PTE de `kmain` en lecture-écriture. Ce chemin contourne toute politique de `vmm_map()`. Refuser une projection dynamique des cadres `PAGETABLE` empêche un **second** alias, mais ne supprime pas le premier.

### 4.5 Mémoire basse et adresses physiques non gérées

- La mémoire basse est entièrement inscriptible dans l'identité, VGA comprise. Seule la VGA en a besoin. Réduire ces droits relève de la « réduction des permissions mémoire » de K0.7, pas de E3.
- `vmm_map()` accepte une adresse physique hors de la mémoire gérée (`FRAME_UNMANAGED`), par exemple le firmware à `0xFFFC0000`, en lecture-écriture. Il n'y a aucun besoin en K0 ; une future projection de périphériques demandera une API dédiée.

## 5. Chemins permettant de modifier `kmain` ou une table de pages

| # | Chemin | État en `e619b7f` |
|---|---|---|
| P1 | écriture directe dans `.text` par l'identité | **bloqué** : PTE en lecture seule + CR0.WP (`pf_write_text`) |
| P2 | `vmm_map(va, page .text, PTE_WRITE)` puis écriture par `va` | **ouvert** (E3) |
| P3 | `vmm_map(va, table de pages, PTE_WRITE)`, puis modification d'une PTE (par exemple rendre `.text` inscriptible) | **ouvert** (E3) |
| P4 | écriture à l'adresse physique d'une table de pages par l'identité, puis modification d'une PTE | **ouvert, par construction** (4.4) |
| P5 | désactiver CR0.WP | aucune API ; une instruction privilégiée suffirait (code ring 0 de confiance) |
| P6 | DMA d'un périphérique | aucun pilote DMA en K0 |

## 6. Constat supplémentaire (non corrigé, hors périmètre)

**C1 — Droits non filtrés dans `map_page()`.** Le contrôle `(flags & ~0xFFFu) != 0` accepte tous les bits bas d'une PTE, y compris `PTE_USER` (0x004), `PWT`/`PCD` (0x008/0x010), PAT (0x080) et `G` (0x100). Une projection dynamique accessible au ring 3 est donc déjà possible. Il n'y a pas de ring 3 en K0, mais ce défaut serait critique en K1. **Correction proposée :** limiter `flags` à `PTE_WRITE`, rapidement, dans un sous-jalon dédié, avec test et contre-épreuve.

## 7. Invariants proposés pour E3

- **A1.** Aucune projection dynamique ne désigne un cadre `FRAME_KERNEL` (code, constantes, données ou structures critiques) : refus `SAMOS_EPERM`. Politique explicite : en K0, l'identité suffit à tous les usages légitimes des données du noyau.
- **A2.** Aucune projection dynamique ne désigne un cadre `FRAME_PAGETABLE` : refus `SAMOS_EPERM`.
- **A3.** Aucune projection dynamique ne désigne un cadre `FRAME_RESERVED` ou `FRAME_UNMANAGED` en K0. La future API de périphériques sera distincte et explicite.
- **A4.** Combinées à M2.4, ces règles ne laissent que les cadres `FRAME_ALLOCATED` projetables dynamiquement (ainsi, A1 à A3 reviennent à : « type ≠ `ALLOCATED` ⇒ refus »).
- **A5.** Tout refus laisse les PTE et les compteurs inchangés : le contrôle de type précède déjà la création de table et la prise de référence dans `map_page()`.
- **A6.** E1, E2, E4 et E5 restent intacts.
- **Limite assumée.** P4 reste ouvert : l'identité garde un alias inscriptible des tables de pages. **E3 ne pourra être déclaré corrigé que pour P2 et P3.**

## 8. Stratégie proposée

| Sous-jalon | Contenu |
|---|---|
| **M2.5b** | Politique : dans `map_page()` compté, refuser tout type autre que `ALLOCATED` (`SAMOS_EPERM`). Le contrôle existe déjà pour `FREE` : c'est une extension minimale. Aucune classification nouvelle n'est nécessaire, car A1-A3 ne dépendent que du type du PMM. |
| **M2.5c** | Corriger C1 (`flags` limité à `PTE_WRITE`). |
| **M2.5d** | Tests : rejouer l'attaque E3 d'origine (alias de `.text`, écriture refusée et code intact), alias de `.rodata`, de la GDT et de la table du PMM, d'une table de pages et de CR3, de la VGA et d'une adresse non gérée. Contre-épreuves isolées. Validation complète. |
| plus tard | P4 : retirer les tables de pages de l'identité (projection récursive ou projection temporaire). Ce changement du VMM est à justifier et à planifier séparément, idéalement avec la migration x86-64. |

**Effet attendu sur les tests existants.** Aucun test actuel ne projette dynamiquement un cadre non `ALLOCATED` avec succès. `test_forbidden_mappings` et `test_vmm_refs` utilisent des cadres alloués. Seule la preuve historique E3 (`k06-evidence.c.txt`, hors du banc de tests) le faisait.
