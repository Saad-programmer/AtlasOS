# K0.7-R1e — Pages de garde de S1 et S2 : cartographie, conception, faisabilité

**Statut :** conception et audit de faisabilité. **Aucun changement dans le dépôt** : ni `linker.ld`, ni les projections, ni les piles, ni les TSS.
**Base :** commit `e4fe7f9`, Clang 18.1.3, GNU ld 2.42, QEMU 8.2.2, `-m 128M`.
**Décision D1 (développeur) :** protéger le sommet de S1 et le bas de S2 par des pages non présentes.
**Méthode :**
- adresses relevées par `nm`, `readelf` et le moniteur QEMU (`info registers`, `info mem`, `xp`) ;
- conception validée par un **prototype jetable**, construit dans une copie isolée hors du dépôt, puis supprimé. Ses résultats sont signalés « (prototype) ».

## 1. Adresses physiques et virtuelles

En K0, toute la RAM gérée est projetée en **identité** (`paging_init`) : pour chaque page présente, l'adresse virtuelle est égale à l'adresse physique. Les tableaux ci-dessous donnent donc une seule adresse, qui est les deux à la fois.

Pour une **page de garde**, il faut distinguer :
- **la page virtuelle** : elle est **non présente** (PTE nulle) ;
- **le cadre physique de même adresse** : il existe. Il est typé `FRAME_KERNEL`, car il est compris dans `[__kernel_start, __kernel_end)`, réservé par `pmm_init`. Il n'est donc **jamais distribué** par le PMM, et **jamais projetable** dynamiquement : `vmm_map` refuse les cadres non `ALLOCATED` (M2.5b). Il n'est projeté nulle part, donc il n'a **aucun alias**.

C'est déjà le cas de la garde basse actuelle de S1.

### 2.3 Constats

1. **Sommet de S1 :** la page immédiatement au-dessus est le **répertoire de pages**, dans les deux images. Elle ne peut pas devenir une garde **sans déplacement**, puisqu'elle est occupée.
2. **Bas de S2 :** S2 ne commence pas sur une frontière de page. Sa première page est partagée avec la GDT et les deux TSS, sa dernière avec l'IDT. **Aucune** page ne peut être retirée sous S2 sans déplacer S2 ou les structures voisines.
3. **Ordre des objets de `.bss` :** il n'est pas garanti. R1d a constaté qu'il change selon l'ordre des définitions dans `gdt.c`. Une garde ne peut pas reposer sur cet ordre.
4. **Pages réservables sans déplacement :** aucune qui convienne. La seule candidate pour S1 serait le cadre `0x191000`, en le réservant dans le PMM avant `paging_init` (le répertoire passerait alors à `0x192000`). Cette solution n'a ni symbole ni vérification à l'édition de liens. Elle est écartée au profit d'une section explicite (section 3).

## 3. Disposition proposée : une section `.stacks` explicite

### 3.1 Principe

Toutes les piles et leurs gardes sont regroupées dans **une seule section NOBITS dédiée**, dont l'ordre interne est fixé par le script de liens. Il ne dépend plus de l'ordre des objets de `.bss`.

```text
.stacks (NOLOAD, ALIGN(4096), segment data)
  __df_guard_start      +4 KiB   garde basse de S2            NON PRÉSENTE
  __df_guard_end = df_stack_area
                        +4 KiB   S2 (pile de double faute)    rw
  __stack_guard_start   +4 KiB   garde basse de S1            NON PRÉSENTE (existante)
                                 = garde AU-DESSUS de S2
  __stack_guard_end = boot_stack_bottom
                        +16 KiB  S1                           rw
  boot_stack_top = __stack_top_guard_start
                        +4 KiB   garde haute de S1            NON PRÉSENTE
  __stack_top_guard_end = __kernel_end   -> premier cadre géré (répertoire de pages)
```

La garde basse actuelle de S1 sépare aussi le **sommet** de S2 du bas de S1 : une page est économisée, et S2 est gardée des deux côtés.

### 3.2 Changements nécessaires

| Fichier | Changement |
|---|---|
| `entry.asm` | `section .dfstack nobits alloc noexec write align=4096`, `global df_stack_area`, `resb 4096` (même méthode que `.bootstack`) |
| `linker.ld` | remplacer la section `.bootstack` par `.stacks` (ci-dessus) ; `KEEP(*(.dfstack))` et `KEEP(*(.bootstack))` ; nouveaux symboles `__df_guard_start`/`__df_guard_end`, `__stack_top_guard_start`/`__stack_top_guard_end` |
| `linker.ld`, assertions | `df_stack_area == __df_guard_end` ; `df_stack_area + 4096 == __stack_guard_start` ; `__stack_guard_end == boot_stack_bottom` (existante) ; `boot_stack_top == __stack_top_guard_start` ; `__stack_top_guard_end == __kernel_end` ; chaque garde alignée sur 4096 et de 4096 octets |
| `gdt.c` | `g_df_stack` devient `extern uint8_t df_stack_area[]`, et quitte `.bss`. S2 n'étant plus remise à zéro par `_start`, **mise à zéro explicite** dans `gdt_init` avant les sentinelles (pour une mesure de profondeur déterministe) |
| `paging.c` | `va_must_stay_unmapped` et la boucle d'identité de `paging_init` traitent les **trois** gardes (table de plages) ; `paging_classify` nomme les nouvelles gardes |
| `kernel.h` | déclaration des nouveaux symboles |
| `layout.c`, `test_layout.c`, `test_boot.c` | table des régions et assertions de contiguïté. `boot_stack_top == __kernel_end` devient `__stack_top_guard_end == __kernel_end` : c'est le seul échec observé dans le prototype |
| `tools/check_elf.sh` | `.stacks` au lieu de `.bootstack` : section NOBITS, ordre, alignement, et symboles de garde alignés |

**Pourquoi NASM pour S2 :** un tableau C placé par attribut dans `.dfstack` est émis en **PROGBITS** (vérifié : 4 KiB de plus dans le fichier). Placé dans `.bss.dfstack`, il serait NOBITS, mais capturé par la règle `*(.bss .bss.*)` de `.bss`. La section NASM `nobits` est la méthode déjà employée pour S1.

## 4. Garde haute de S1

### 4.1 Garanties

- Page non présente immédiatement au-dessus de `boot_stack_top`, exclusive par construction (`. += PAGE_SIZE` dans `.stacks`) : aucun objet ne peut y être placé.
- **Aucune écriture légitime :**
  - `_start` empile ses arguments sous le sommet (`ESP = sommet - 8`, puis deux `push`) ;
  - `boot_stack_high_water` lit `[bottom, top)` ;
  - `stack_collect` refuse `ebp > hi - 8` ;
  - `esp0` du TSS principal vaut le sommet, mais ne sert qu'à une transition ring 3 vers ring 0, absente en K0.
- **Avant la pagination :** la page est de la RAM ordinaire, non protégée, et rien n'y écrit (la peinture de `_start` couvre `[__stack_guard_start, boot_stack_top)`).
- **Après la pagination :** elle est non présente.
- La garde basse existante est conservée, inchangée dans sa fonction.

### 4.2 Ce qui est détecté, et ce qui ne l'est pas

Une garde **haute** ne protège **pas** contre le débordement classique, qui descend : c'est le rôle de la garde basse. Elle intercepte les accès **au-dessus** du sommet.

| Scénario | Résultat |
|---|---|
| Écriture vers le haut depuis un tableau local d'un cadre proche du sommet (`kmain`, qui ne retourne jamais, donc sans canari utile) | **#PF** à l'adresse fautive. Elle est livrée sur S1, encore valide, donc le gestionnaire ordinaire s'exécute, puis `panic` |
| Dépilage excessif (`ret` ou `pop` de trop, erreur d'assembleur) qui fait passer ESP au-dessus du sommet, puis accès | **#PF** |
| Lecture des « arguments » d'un appelant inexistant au-delà du sommet | **#PF** |
| Écriture au-delà de la garde (plus de 4 KiB au-dessus du sommet) | **non détectée** : elle atteint le répertoire de pages, désormais à sommet + 4 KiB |
| Corruption **à l'intérieur** de S1 (cadre voisin, adresse de retour) | non détectée par la garde (canaris de R1c, partiellement) |
| Débordement vers le bas | garde basse, inchangée |

Prototype : `mem_probe_write(__stack_top_guard_start)` donne -1, CR2 = l'adresse de la garde, code d'erreur 2 (page non présente, écriture).

## 5. Garde basse de S2

### 5.1 Garanties

- **Page non présente** immédiatement sous S2 (`__df_guard_start`, exclusive).
- **S2 :** 4096 octets entièrement utilisables, alignés sur 4096. Mesure R1d : le chemin #DF complet en utilise 848.
- **TSS et GDT :** ils restent dans `.bss`, loin de `.stacks`. Ils ne peuvent plus partager une page avec S2 ni avec une garde.
- **`g_tss_df.esp`** = `df_stack_area + 4096` ; l'initialisation du TSS est inchangée.
- **Sentinelles de R1d :** conservées aux 16 premiers octets de S2. Elles détectent toujours une écriture parasite dans le bas de S2, et la garde arrête tout ce qui descend plus bas.
- **Aucun recouvrement :** les assertions de l'éditeur de liens le garantissent (section 3.2), et `check_elf.sh` le revérifie.

### 5.2 Faute pendant le traitement d'une double faute : triple fault

Si la tâche #DF déborde de S2 :

1. Le premier accès à la garde provoque une **#PF**.
2. La #PF passe par une porte d'interruption ring 0, donc sur **la même pile** : le CPU doit empiler son cadre sur S2, dans la garde.
3. Cet empilement échoue : c'est une faute pendant la livraison d'une faute, donc une **#DF**.
4. La #DF passe par une porte de tâche vers `g_tss_df`, **déjà occupé** (la tâche courante) : la livraison échoue.
5. Résultat : un **triple fault**, puis l'arrêt du CPU (QEMU `-no-reboot` s'arrête).

**Mesure (prototype, débordement volontaire de S2 dans la tâche #DF) :**

```text
v=08 ... SP=0010:0019df70            <- #DF initiale (tâche #DF sur S2)
v=0e e=0002 ... SP=0010:00198000 CR2=00197ffc   <- #PF : écriture du premier mot SOUS S2
v=08 ... SP=0010:00198000            <- #DF pendant la livraison de la #PF
Triple fault
```

Le résultat est **déterministe**, et **rien n'est écrit sous S2**. Sans garde, avec la disposition actuelle, le même débordement écrirait d'abord dans `g_tss_df`, puis `g_tss_main` et la GDT, sans aucune faute.

**Aucune récupération n'est promise.** Une #DF est déjà une faute irrécupérable (« abort »). La garde vise l'**isolation** : empêcher qu'un débordement de S2 corrompe les TSS, la GDT ou d'autres données, et rendre la fin déterministe. Le diagnostic se limite à ce que la tâche #DF a affiché avant le débordement, et à la détection du triple fault par le banc de tests.

Faute ordinaire dans la tâche #DF sans épuisement de S2 (accès à une page non projetée, par exemple) : la #PF est livrée normalement sur S2, puis le gestionnaire appelle `panic`. Pas de triple fault.

## 6. Risques de démarrage

| Risque | Analyse | Mesure |
|---|---|---|
| Code exécuté avant la pagination qui touche une garde | aucun accès dans `_start`, `kmain` jusqu'à `mm_init`, ni dans `gdt_init` (S2 n'est écrite que dans `[df_stack_area, +4096)`) | prototype : démarrage normal, peinture et profondeur inchangées (852 octets) |
| S2 non remise à zéro (hors de `.bss`) | contenu indéfini au chargement ; sans effet sur le fonctionnement | mise à zéro explicite dans `gdt_init` |
| PMM | les gardes sont dans l'image, donc `FRAME_KERNEL`, non distribuées | aucune modification du PMM |
| Projections d'identité | la boucle doit sauter les trois gardes **et** `vmm_map` doit les refuser (E2 généralisé) | prototype : `vmm_map(garde haute)` et `vmm_map(garde S2)` renvoient `EPERM` |
| Répertoire de pages déplacé | aucune adresse codée en dur ; CR3 provient de `pmm_alloc_pagetable` | prototype : CR3 = `0x193000`, démarrage normal |
| Tests de disposition existants | `boot_stack_top == __kernel_end` devient faux | à adapter (section 3.2) |
| Taille de l'image | assertion `__kernel_end <= 4 MiB` : `0x193000` | marge suffisante |

**Prototype, synthèse :**
- démarrage de production : statut 124, « boot complete » ;
- autotests : 478 vérifications, 1 échec attendu (`boot_stack_top == __kernel_end`) ;
- `df`, `stack`, `dfsentinel` et `canary` : statut 37, aucun triple fault ;
- `info mem` montre trois trous : `0x18b000`, `0x18d000` et `0x192000` ;
- sondes : écriture dans la garde haute, -1 ; lectures du premier et du dernier mot de la garde S2, -1.

## 9. Limites qui resteront après R1f

- Une écriture **au-delà** d'une garde (plus de 4 KiB) n'est pas arrêtée : au-dessus de la garde haute se trouve toujours le répertoire de pages. Le risque P4 (tables de pages inscriptibles par l'identité) reste ouvert.
- Un débordement de S2 se termine par un **triple fault**, sans diagnostic propre au-delà de ce qui a déjà été affiché.
- Les gardes ne détectent rien **à l'intérieur** d'une pile.
- `-Wframe-larger-than=3072` reste nécessaire pour qu'aucun cadre ne saute une garde de 4 KiB.
