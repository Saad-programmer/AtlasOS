# K0.7-R1 — Canaris de pile du noyau : audit et conception

**Statut :** R1a, audit et conception. **Aucune protection effective n'a été modifiée** : le noyau est toujours compilé avec `-fno-stack-protector`.
**Base auditée :** commit `3194ab6`, Clang 18.1.3, NASM 2.16.01, GNU ld 2.42, QEMU 8.2.2.
**Méthode :** lecture du code et du script de liens, mesures sur les images, et compilations d'essai hors du dépôt (section 3). Chaque affirmation sur Clang a été vérifiée sur la version installée.

## 1. Inventaire des piles

### 1.1 Piles réellement utilisées

| # | Pile | Emplacement (image de production) | Taille | Qui l'utilise | Protection actuelle |
|---|---|---|---|---|---|
| S0 | pile du chargeur | indéfinie (Multiboot ne fournit pas d'ESP valide) | — | aucune instruction : `_start` charge ESP avant tout accès à la pile | sans objet |
| S1 | **pile de démarrage** `boot_stack` | `.bootstack` (NOLOAD) : `0x0018d000`-`0x00191000` | 16 KiB | `kmain`, tout le code C, **toutes les interruptions et exceptions** (sauf #DF) | page de garde **non projetée** en dessous (`0x0018c000`), motif `0x5AFE57AC` pour la mesure de profondeur |
| S2 | **pile de double faute** `g_df_stack` | `.bss` : `0x00109110`-`0x0010a110` | 4 KiB | la tâche matérielle #DF (`double_fault_task`, puis `panic`) | **aucune** |

Il n'y a pas d'autre pile : pas de processus, pas de pile par interruption.

### 1.2 Interruptions, exceptions et double faute

- Les 48 vecteurs (exceptions 0-31, IRQ 32-47) passent par des **portes d'interruption ring 0**. Sans changement de privilège, le processeur **ne change pas de pile** (SDM vol. 3A §6.12.1) : `EFLAGS`, `CS`, `EIP` (et le code d'erreur) sont empilés sur S1, puis `isr_common` y ajoute `pushad` et les segments.
- `g_tss_main.esp0 = boot_stack_top` n'est utilisé que lors d'une transition ring 3 → ring 0, qui n'existe pas en K0.
- Les portes d'interruption masquent IF : les IRQ ne s'imbriquent pas. Une exception pendant une exception est refusée (`g_exc_depth`, puis `panic("nested exception")`), sauf la #PF attendue d'une sonde.
- **#DF passe par une porte de tâche** : le processeur sauvegarde l'état dans `g_tss_main` et charge `g_tss_df` (ESP = sommet de S2, CR3 = celui du noyau). C'est ce qui permet de traiter un débordement de S1 : la #PF sur la page de garde ne peut pas être livrée sur S1, donc la #DF est livrée sur S2 (cas `stack_overflow`).

### 1.3 Mesures

| Mesure | Valeur | Source |
|---|---|---|
| Profondeur maximale de S1 au démarrage de production | **836 octets** sur 16 384 | `boot stack high-water`, journal série |
| Plus grand cadre de pile du noyau (hors tests) | `kvprintf` : 300 octets | `-fstack-usage` (copie isolée) |
| Plus grand cadre de l'image de test | `consume_stack` : 2052 octets (volontaire) | `-fstack-usage` |
| `alloca`, VLA | aucun (`-Wvla` actif) | recherche dans le code |

### 1.4 Voisinage des piles (le point le plus important de l'audit)

```text
S2 (g_df_stack, .bss)                       S1 (boot_stack)
0x00109000 g_gdt                            0x0018c000 page de garde (non projetée)
0x00109030 g_tss_main                       0x0018d000 boot_stack_bottom
0x001090a0 g_tss_df                              ... croissance vers le bas ...
0x00109110 g_df_stack  (bas)                0x00191000 boot_stack_top == __kernel_end
0x0010a110 g_idt       (= sommet de S2)     0x00191000 premier cadre géré : RÉPERTOIRE DE PAGES (CR3)
```

- **S2 n'a aucune garde.** Un débordement de S2 écrase **`g_tss_df`, `g_tss_main`, puis la GDT**, sans aucune faute.
- **S1 n'a pas de garde au-dessus.** `boot_stack_top` coïncide avec le premier cadre géré par le PMM, qui est le **répertoire de pages** (CR3 = `0x00191000`). Une écriture au-delà du sommet, par exemple un tableau local de `kmain` débordant vers le haut, modifie le répertoire de pages sans faute.
- La page de garde sous S1 n'arrête que les accès qui **tombent dedans**. Un cadre de plus de 4 KiB peut la **sauter** (section 3.4) et atteindre `.bss`, et donc `g_meta`, la table du PMM.

## 2. Risques de corruption

| # | Scénario | Effet | Détection actuelle |
|---|---|---|---|
| K1 | dépassement d'un tableau local vers le haut, dans un cadre | adresse de retour et EBP sauvegardé écrasés ; retour vers une adresse arbitraire | **aucune** (au mieux #UD, #PF ou #GP plus tard, sans lien avec la cause) |
| K2 | débordement progressif de S1 (récursion, cadres empilés) | accès à la page de garde | **oui** : #PF puis #DF sur S2, `panic` (cas `stack_overflow`) |
| K3 | cadre de plus de 4 KiB sous un ESP proche du bas de S1 | écriture **sous** la garde, dans `.bss` (`g_meta`) | **aucune** |
| K4 | écriture au-dessus de `boot_stack_top` | répertoire de pages modifié | **aucune** |
| K5 | débordement de S2 pendant le traitement d'une #DF | TSS et GDT écrasés | **aucune** |
| K6 | pointeur parasite vers la pile (hors cadre courant) | données d'un autre cadre modifiées | **aucune** (hors de portée des canaris) |

## 3. Mécanisme A : canaris de fonctions (instrumentation du compilateur)

### 3.1 Ce que produit Clang 18 pour `i686-unknown-none-elf` (vérifié)

Fonction `arr` contenant `char b[16]`, compilée avec `-fstack-protector-strong -O2` :

```asm
movl  __stack_chk_guard, %eax   ; prologue : copie du canari global
movl  %eax, -4(%ebp)            ;            juste sous l'EBP sauvegardé
...                             ; corps (b est sous le canari)
movl  __stack_chk_guard, %eax   ; épilogue : comparaison
cmpl  -4(%ebp), %eax
jne   .LBB1_2
...   retl
.LBB1_2: calll __stack_chk_fail ; jamais de retour attendu
```

- **Symboles attendus :** `__stack_chk_guard` (donnée de 32 bits) et `__stack_chk_fail` (fonction). Aucun autre support d'exécution n'est nécessaire, et pas de libc.
- **Stockage :** une **variable globale**. Sur cette cible, `-mstack-protector-guard=tls` et `-mstack-protector-guard-symbol=` sont **ignorés sans avertissement** : le symbole reste `__stack_chk_guard`, et il n'y a pas d'accès `%gs:`.
- **Couverture mesurée** sur 5 fonctions types (sans tableau, tableau, adresse d'un local prise, attribut d'exclusion, cadre de 8 KiB) :

| Option | Fonctions instrumentées |
|---|---|
| `-fstack-protector` | tableaux de type `char` (y compris le cadre de 8 KiB) |
| `-fstack-protector-strong` | + fonctions dont l'adresse d'un local est prise |
| `-fstack-protector-all` | toutes, y compris les fonctions triviales |

- **Exclusion :** `__attribute__((no_stack_protector))` est respecté. L'attribut inverse `stack_protect` est **inconnu** de Clang 18 (`-Wunknown-attributes`) : on ne peut pas activer la protection fonction par fonction, seulement **fichier par fichier** (options de compilation).

### 3.2 Valeur et initialisation du canari

**Contrainte fondamentale :** la valeur ne doit jamais changer pendant qu'une fonction instrumentée est active. Sinon, son épilogue compare une copie ancienne à la nouvelle valeur et appelle `__stack_chk_fail` à tort.

| Option | Analyse | Choix |
|---|---|---|
| initialisation en C dans `kmain` | `kmain` est déjà actif ; il faudrait l'exclure, ainsi que tout appelant en cours. Fragile. | non |
| **initialisation en NASM dans `_start`**, après la remise à zéro de `.bss`, avant `call kmain` | aucun cadre C n'existe encore : aucune copie ancienne possible. | **oui** |

- **Entropie :** `RDTSC` (disponible sur tout i686), lu en NASM. Valeur proposée : `(TSC bas ⊕ rotation(TSC haut) ⊕ constante) & 0xFFFFFF00`, forcée non nulle.
  - L'**octet de poids faible est nul** (canari « terminateur ») : une copie de chaîne débordante s'arrête au NUL et ne peut pas réécrire le canari intact.
  - Limite : le TSC au démarrage est peu imprévisible (temps de démarrage quasi constant sous QEMU). La menace visée en K0 est la **corruption accidentelle**, pas un attaquant qui devine la valeur.
- **Emplacement :** `__stack_chk_guard` est défini en **NASM dans `.rodata`**.
  - Il est écrit une seule fois par `_start`, **avant l'activation de la pagination** : aucune protection n'existe encore, l'écriture réussit.
  - Une fois CR0.PG et CR0.WP actifs, la page est en lecture seule, même pour le ring 0 : **le canari ne peut plus être modifié** par une écriture parasite.
  - Il ne faut **pas** le déclarer `const` en C : le compilateur pourrait remplacer sa lecture par la valeur initiale. Le C ne le déclare pas du tout ; le code instrumenté y accède comme à un symbole externe.
  - Il ne doit pas être dans `.bss`, que `_start` remet à zéro.

### 3.3 `__stack_chk_fail` : réaction déterministe

- `noreturn`, `no_stack_protector`, en C dans un fichier dédié.
- Il masque les interruptions (`cli`), puis appelle `panic("stack smashing detected (canary), caller %p", __builtin_return_address(0))`. L'adresse de retour désigne la fonction fautive, car elle est saine : c'est le canari, plus haut dans le cadre, qui a été détruit.
- Il s'exécute **sur la même pile**, ce qui est sûr : ESP est valide (l'épilogue n'a pas encore dépilé le cadre corrompu), et `__stack_chk_fail` ne retourne jamais. La trace de `panic` (`stack_collect`) est bornée à S1 et vérifie la monotonie de la chaîne EBP : un EBP sauvegardé corrompu l'arrête proprement.
- Les statuts restent ceux du banc : 37 (panique) dans l'image de test, arrêt en production. `panic_at` gère déjà la récursion (`RECURSIVE PANIC`, sortie minimale).

### 3.4 Fonctions sans instrumentation

| Fonction | Raison |
|---|---|
| `_start` (NASM) | non instrumentable ; c'est elle qui initialise le canari |
| `__stack_chk_fail` | sinon, récursion à l'infini |
| `panic_at`, `stack_collect`, `emergency_puts` | chemin de réaction : il doit rester minimal même si l'état est corrompu (`panic_at` contient un tableau local, donc il serait instrumenté) |
| `isr_stubs.asm`, `probe.asm`, `gdt_flush.asm` | NASM, non concernés |
| `double_fault_task` | **peut** être instrumentée (canari global identique, pile S2 valide), mais elle ne retourne jamais : l'instrumentation n'y apporte rien |
| `kmain`, `idle_loop` | instrumentables (la valeur est fixée avant), mais sans effet utile, car ils ne retournent jamais |

### 3.5 Couverture et limites du mécanisme A

- Il détecte **K1** (écriture continue vers le haut depuis un tableau local) **au retour** de la fonction : entre la corruption et le retour, le code continue de s'exécuter avec un cadre corrompu.
- Il ne détecte pas :
  - une fonction qui ne retourne jamais (`kmain`) ;
  - une écriture qui saute le canari (index arbitraire, K6) ;
  - la corruption de variables locales situées **au-dessus** du tableau dans le même cadre (Clang les réordonne en partie) ;
  - K2 à K5.
- Coût : deux lectures, une comparaison et un branchement par fonction instrumentée ; image légèrement plus grande (mesures en R1c).

## 4. Mécanisme B : canaris de frontières de piles (sentinelles)

Une sentinelle est un mot de valeur connue posé à la **limite basse** d'une pile, et vérifié par logiciel à des moments choisis. C'est un mécanisme **distinct** du précédent. Il ne protège aucune fonction en particulier : il constate *a posteriori* qu'une pile a atteint sa limite.

| Pile | Emplacement sûr | Intérêt |
|---|---|---|
| S2 (`g_df_stack`) | les premiers mots du tableau (bas de S2), juste au-dessus de `g_tss_df` | **réel** : S2 n'a pas de garde ; une sentinelle détruite signale que S2 a débordé, ou presque (K5) |
| S1 | les mots juste au-dessus de la page de garde | **faible** : un débordement progressif touche la garde (faute matérielle immédiate) avant de pouvoir être constaté ; la sentinelle ne ferait que signaler une marge épuisée. Le motif actuel donne déjà la profondeur maximale |
| S1, côté sommet | impossible sans changer la disposition (le sommet touche le répertoire de pages) | voir la décision D1 |

- **Moments de vérification possibles :** après l'initialisation, dans `double_fault_task` (sur S2 même, avant `panic`), dans `panic`, à chaque tic de l'horloge (coût : quelques lectures), et dans les autotests.
- **Limites :**
  - Détection différée : le code a déjà continué avec une pile corrompue.
  - Un débordement **brutal** qui saute la sentinelle sans l'écrire n'est pas vu.
  - Une sentinelle réécrite avec la même valeur n'est pas vue (improbable).
  - Une #DF dont S2 déborde réellement aura déjà écrasé les TSS : la vérification sert au diagnostic, pas au rétablissement.
- **Avec les pages de garde :** les gardes sont **matérielles et immédiates**, mais n'existent que sous S1. Les sentinelles sont **logicielles et différées**, mais applicables à S2. Les deux se complètent ; aucune ne remplace l'autre.

## 5. Mesure complémentaire, indépendante des canaris : borne sur la taille des cadres

- Clang ne fournit pas `-fstack-clash-protection` pour cette cible (option ignorée, avertissement « unused »). Un cadre de 8 KiB est alloué par `subl $8192, %esp`, sans sondage : il peut **sauter la page de garde** (K3).
- **`-Wframe-larger-than=N`** (vérifié avec `-Werror` : « stack frame size (5004) exceeds limit (4000) ») refuse à la compilation tout cadre plus grand que N.
- **Raisonnement :** si chaque cadre est inférieur à 4096 octets, l'adresse la plus basse qu'il touche est au moins `ESP_avant - 4095`, donc dans la garde ou au-dessus. La garde ne peut plus être sautée. Sans `alloca` ni VLA (déjà interdits), aucun cadre n'échappe à cette borne.
- **Seuil proposé :** 3072 octets. Le plus grand cadre actuel fait 2052 octets (`consume_stack`, test volontaire). Le seuil laisse une marge sous 4096 pour les arguments empilés et le cadre d'interruption.

## 6. Stratégie retenue pour K0.7

| Élément | Décision |
|---|---|
| Canaris de fonctions | `-fstack-protector-strong`, dans **les deux images** (c'est une protection, pas un outil de test) |
| Valeur | NASM dans `.rodata` ; écrite par `_start` avant `kmain` et avant la pagination ; lecture seule ensuite (CR0.WP) |
| Entropie | `RDTSC` mélangé, octet faible nul, non nul |
| Échec | `__stack_chk_fail`, puis `panic` ; chemin de réaction exclu de l'instrumentation |
| Introduction progressive | d'abord **un seul fichier de test** instrumenté (option par fichier), puis tout le noyau |
| Borne des cadres | `-Wframe-larger-than=3072` |
| Sentinelles | bas de S2, vérifiées dans `double_fault_task`, `panic` et les autotests |
| Dépendances | aucune : pas de libc, pas d'allocation, pas de nouvel outil |

**Compatibilité vérifiée par l'analyse :**
- i386 et NASM : accès global simple.
- Pagination et WP : écriture unique avant CR0.PG.
- Interruptions : le canari global est identique pour toutes les piles, et le dispatcher C est instrumenté comme une fonction ordinaire.
- Exceptions imbriquées : déjà refusées ; un échec de canari pendant une exception mène à `panic`.
- Double faute : S2 utilise la même valeur, et une corruption détectée sur S2 mène à `panic`.

## 10. Critères d'acceptation de R1

1. Les deux images sont compilées avec `-fstack-protector-strong`, sauf les fonctions exclues et justifiées (section 3.4), et `-Wframe-larger-than=3072`.
2. `__stack_chk_guard` est initialisé avant le premier code C, est non nul avec un octet faible nul, et se trouve dans une page en lecture seule après la pagination (T2, T3, `check_elf`).
3. Une corruption contrôlée déclenche `panic` « stack smashing detected », de façon déterministe (T1), sans triple fault.
4. Les contre-épreuves C1 à C3 sont détectées par le moteur de mutation, avec des assertions nommées.
5. La sentinelle de S2 détecte sa destruction (T6).
6. Aucune régression : `make test` (26 cas QEMU), `make test-mutation`, `make test-repro`.
7. Les limites (sections 3.5 et 4, risques K2 à K6, D1) sont documentées sans exagération : **les canaris ne protègent pas contre toutes les corruptions de pile.**
