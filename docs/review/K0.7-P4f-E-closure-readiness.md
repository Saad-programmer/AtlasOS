## 1. N1 — contre-vérification

### 1.1 Code machine (image de production)

Tous les chemins d'allocation passent par `alloc_zeroed` : `pmm_alloc_frame` et `pmm_alloc_pagetable` y sautent directement (`jmp alloc_zeroed`). Le seul autre point qui écrit sur un cadre distribué est `pmm_core_alloc_as`, qui n'écrit que dans `g_meta`. `pmm_core_alloc` n'est appelé que par le banc hébergé.

**Graphe de contrôle relevé dans `alloc_zeroed` :**

```
call pmm_core_alloc_as
cmp $0x100000,%edi ; jb  → [motif "low memory"]  → page_checksum → panic_at
cmp image (0x100000..__kernel_end) ; jb → [motif "kernel image"] → page_checksum → panic_at
parcours de g_boot_map ; région non disponible ou cadre hors région → page_checksum → panic_at
(sinon) call memset(phys, 0, 4096) ; ret
```

**Le seul `call memset` (`0x105fb7`) n'est atteignable qu'après les trois contrôles.** Aucun chemin protégé ne revient vers lui, car `panic_at` ne rend pas la main. Classe : CONTRÔLÉ STATIQUEMENT (relevé manuel, aucune règle automatique dans `check_elf.sh`).

### 1.2 Expérience précise (GDB, image de test non modifiée)

Le critère de P4f-D, « empreinte différente de celle d'une page nulle », était **trop faible** pour la pile active et la VGA. Je l'ai remplacé par la méthode suivante :
- un point d'arrêt sur l'appel `vmm_map` du mode destructif, puis un **vidage** des 4 KiB du cadre ;
- un point d'arrêt **conditionnel sur `memset`**, déclenché si sa destination tombe dans le cadre ;
- un point d'arrêt à l'entrée de `panic_at`, puis un second vidage.

| Mode | Cadre | `memset` sur le cadre | Octets différents entre les deux vidages | Interprétation |
|---|---|---|---|---|
| `n1low` (VGA) | `0x000b8000` | **jamais** | **0 / 4096** | page strictement intacte jusqu'à la panique |
| `n1gdt` | `0x00124000` | jamais | **0 / 4096** | intacte |
| `n1data` | `0x00123000` | jamais | **0 / 4096** | intacte |
| `n1stack` (pile active) | `0x001b1000` | jamais | 145, **tous** dans `0x001b1e04-0x001b1eff`, strictement **sous** l'ESP du premier vidage (`0x001b1f00`) | seuls les cadres d'appel plus profonds (`vmm_map` → … → `panic_at`) ont été écrits ; aucun octet de la pile au-dessus de l'ESP n'a changé |

Classe : **PROUVÉ PAR TEST**, jusqu'à l'entrée de `panic_at`.

**Limites :**
- après l'entrée de `panic_at`, la panique écrit elle-même en VGA (affichage), ce qui est légitime ;
- l'expérience porte sur QEMU (TCG), pour les modes de test, et à la main : elle n'est pas intégrée au banc automatique.

### 1.3 Limites restantes de N1

- **Critère « carte du démarrage » (`g_memmap`) :** NON TESTÉ. Aucune région réservée ne se trouve dans la mémoire gérée sous QEMU.
- **Falsification conjointe** de `g_meta` et `g_memmap` : non couverte (P4f-D §8).
- **Fiabilité de la seconde couche :** elle n'est démontrée que par la mutation M59.

- **Au démarrage**, `kmain` exécute l'audit **une fois**, après le scellement. Toute incohérence présente à ce moment arrête le noyau.

## 4. N3 — analyse complète

### 4.1 Reproduction (copie jetable, image de test, 128 MiB)

| Étape | Observé |
|---|---|
| projection légitime | `x = 0x001d5000` projeté RW à `0xD0001000` ; descripteur `0x0013` (type 3 = ALLOCATED, refs = 1) ; PTE `0x001d5063` |
| libération légitime tentée | `pmm_free_frame(x)` = **−9 (EBUSY)** : le compteur protège |
| **falsification** | une écriture de 16 bits : descripteur `0x0013` → `0x0003` (**champ `refs`**, bits 4-15, de 1 à 0) ; `pmm_core_check` = 0 (rien n'est vu) |
| libération | `pmm_free_frame(x)` = **0** (`pmm_core_free` : type ALLOCATED et refs = 0, donc FREE) |
| réattribution | `pmm_alloc_frame` (next-fit) rend **le même cadre** (`y == x`), remis à zéro, à un nouveau propriétaire, qui y écrit `0x5EC12E70` |
| ancienne projection | toujours présente : elle **lit** `0x5ec12e70` (le secret du nouveau propriétaire), puis **écrit** `0x0badc0de`, que le nouveau propriétaire **voit** : fuite **et** corruption croisée, dans les deux sens |
| audit | **propre** (`ok=1`) : un alias d'un cadre ordinaire n'est pas un alias interdit |
| tentative de retrait de l'ancienne projection | `vmm_unmap` = **−1 (EINVAL)** : refs = 0 pour un cadre ALLOCATED est vu comme une incohérence ; la projection **reste en place** |
| variante « type seul » | descripteur d'un cadre projeté := FREE (`free_count + 1`), sans `pmm_free_frame` : **réattribution du cadre encore projeté** |
| autres structures : table de pages retypée ALLOCATED, refs 0, libérée | la libération réussit ; à la réattribution, la remise à zéro faute sur l'identité **scellée** : panique (#PF, « protection violation ») ; arrêt fail-stop, mais le diagnostic est générique, car le classement des fautes dépend du type PMM |
| image, mémoire basse | réattribution refusée avant toute écriture (N1, P4f-D) |

**Réponses :**
- **Métadonnée falsifiée :** le champ `refs` du descripteur (ou le type, dans la variante).
- **Libération :** `pmm_free_frame` → `pmm_core_free`, qui se fie à `refs`.
- **Réattribution :** `pmm_alloc_frame` → `alloc_zeroed` (next-fit), qui se fie au type FREE.
- **Ancienne projection :** **accessible**, et non retirable par `vmm_unmap`.
- **Fuite et corruption croisée :** **observées**.
- **Périmètre :** **uniquement les cadres de données ordinaires** projetés par `vmm_map`. Les tables de pages sont protégées par l'identité scellée et D1, l'image et la mémoire basse par N1.

### 4.2 Portée réelle dans K0

- **Aucun code de production n'appelle `vmm_map`** (relecture : `vmm_map` et `vmm_unmap` n'ont d'appelants que dans `paging.c` et les tests). En K0, les projections dynamiques n'existent que dans les autotests.
- **Il n'y a qu'un espace d'adressage, en ring 0,** et toute la RAM gérée est déjà projetée en RW dans l'identité. Quiconque peut écrire dans `g_meta` (données RW) peut écrire directement dans n'importe quel cadre de données. **N3 ne donne donc aucune capacité nouvelle à un attaquant en K0.**
- **N3 deviendra important avec K1**, dès qu'existeront des espaces d'adressage distincts (projections utilisateur) et des propriétaires de cadres qui ne se font pas confiance. C'est alors une faille d'**isolation** directe.

### 4.3 Options

| Critère | **Option A** : risque résiduel documenté | **Option B** : vérification indépendante avant libération et réattribution (prototype mesuré) |
|---|---|---|
| Principe | aucune modification ; N3 consigné comme précondition de K1 | `pmm_free_frame` refuse (EBUSY) un cadre encore projeté hors identité ; `alloc_zeroed` refuse (panique) de distribuer un tel cadre. Critère : parcours des PTE à `va ≥ g_idmap_top` dans les tables publiées (RO) — la fonction `frame_has_foreign_alias` de P4f-B1, sans le PMM |
| Effet sur N3 | aucun | prototype : libération falsifiée **refusée** (−9), le nouveau propriétaire reçoit un **autre** cadre, l'ancienne projection ne voit que ses propres données ; variante « type seul » : panique **avant** remise à zéro (`still mapped outside identity`) |
| Complexité | nulle | faible : environ 10 lignes, une fonction exportée du VMM vers le PMM |
| Couplage | — | **nouveau couplage PMM → VMM** (le PMM appelle le VMM) ; inversion de dépendance à documenter, ou vérification placée dans une enveloppe du VMM |
| Mémoire | 0 | 0 |
| Temps | 0 | `pmm_alloc_frame` + `pmm_free_frame` ×1000 : **72,4-73,1 M** (×1024 cycles, TCG) contre 24,0-37,9 M, soit environ **×2 à ×3** avec quelques tables dynamiques. Le coût croît **linéairement** avec le nombre de tables hors identité (1 024 PTE lues par table et par opération). `vmm_map`/`vmm_unmap` inchangés |
| Nouveaux risques | — | (a) le PMM dépend de l'intégrité des tables (RO, protégées par P4e-2 et D3 : cohérent) ; (b) un refus EBUSY sur une libération légitime est impossible si l'appelant retire bien ses projections avant de libérer (autotests : 727 vérifications, 0 échec dans le prototype) ; (c) les alias d'identité ne sont pas vus, ce qui est voulu (l'identité projette toute la RAM) ; (d) ne corrige pas le choix de `vmm_unmap` fondé sur le type PMM (« counted ») |
| Limites de preuve | — | prototype non intégré, mesuré sous TCG seulement ; ne protège pas des projections futures d'autres espaces d'adressage (K1 : il faudra parcourir **tous** les répertoires, ou tenir un compte indépendant) |
| Alternative B′ | — | comptes de projections **indépendants** (un compteur par cadre dans une page scellée, écrite par le passage) : en temps O(1), mais 2 octets par cadre (512 KiB pour 1 GiB) et une nouvelle structure de confiance à écrire par une fenêtre WP. Changement d'architecture, à étudier en K1 |

**Recommandation :**
- **Option A pour la clôture de P4**, puisque N3 n'a aucune exposition en K0 et ne donne aucune capacité nouvelle.
- **Option B (ou B′) comme précondition explicite de K1**, à mettre en œuvre avant toute projection d'un espace d'adressage non noyau.

## 5. Performance (N4)

| Configuration (TCG, ×1024 cycles, 1 000 couples `vmm_map` + `vmm_unmap`) | Mesure |
|---|---|
| état actuel (`78b172ba`) | 31,3-33,2 M |
| prototype « préfiltre d'identité » | 23,0-23,3 M (deux mesures sur trois ; une valeur isolée à 39,2 M, attribuée au bruit de TCG, non expliquée) |
| P4d, avant le passage (rappel de P4f-C) | 1,7-2,6 M |

**Optimisation simple identifiée** (prototype seulement, non intégrée). Sous pagination, **toute structure publiée est scellée** : identité sans W, invariant de P4e-2 et du passage, indépendant du PMM. Dans `frame_is_paging_structure`, une identité **inscriptible** permet donc de répondre « non » sans parcourir les 1 024 PDE ; le parcours complet reste nécessaire **avant** l'activation de la pagination, quand les tables ne sont pas encore scellées. Le prototype :
- passe les autotests (727 vérifications), `pmmtrust`, `pdeint`, `tablelife` et `imageint` ;
- réduit le coût d'environ 30 % sous TCG.

La garantie repose sur un invariant **déjà prouvé** (I3 et I6 de P4f-C). À intégrer éventuellement avec une mutation dédiée, sur autorisation. **Ni le VMM ni le mécanisme CR0.WP n'ont été modifiés.**

Le reste de l'écart avec P4d vient de la fenêtre CR0.WP (vidage du TLB sous QEMU, artefact de l'émulateur) et des autres contrôles. Sur matériel réel, le coût est **NON MESURÉ**.

## 7. Régressions et défauts découverts

**Aucune régression des garanties D1 à D4 ou N1, N2, N5.**

Trois constats, sans gravité CRITICAL ou HIGH :
1. **LOW :** le critère de P4f-D « empreinte différente d'une page nulle », pour la pile et la VGA, était insuffisant. Il est remplacé ici par une preuve exacte (§1.2). Le banc automatique garde le critère faible pour ces deux modes. Amélioration possible : intégrer la comparaison par GDB au banc (`make test-gdb`).
2. **LOW :** le diagnostic d'une #PF sur une table réutilisée dépend du type PMM (§4.1).
3. **INFO :** l'audit lit le contenu d'un cadre de l'image comme des PTE s'il est désigné par une PDE forcée. C'est une lecture, sans effet.

## 9. Recommandation et décision

**A — P4 peut être clôturé sous hypothèses et risques explicitement acceptés.**

**Justification :**
- Les correctifs N1, N2 et N5 sont confirmés **indépendamment** :
  - code machine de l'allocateur (§1.1) ;
  - preuve octet par octet avec GDB que les pages protégées ne sont pas écrites avant la panique, pile active et VGA comprises (§1.2) ;
  - refus du passage sans l'allocateur, avec PDE, PTE, références, fenêtres et CR0 inchangés (§2) ;
  - chaque compteur d'audit détecte sa violation (§3).
- D1 à D4 restent valides (§8).
- N3 est **réel**, mais limité aux cadres de données ordinaires. Il n'a **aucune exposition** en K0 (aucun utilisateur de `vmm_map` en production, espace unique en ring 0, RAM déjà inscriptible par l'identité) et ne donne aucune capacité nouvelle. Il ne touche pas les structures que P4 protège : tables, image, structures critiques.
- Aucun défaut ne justifie B. Aucune hypothèse architecturale ne doit être revue (C).

**Conditions de cette décision**, à accepter **explicitement** par le développeur. Sans cette acceptation, la décision est B :
1. GDT/TSS inscriptibles (HIGH).
2. NMI ou #MC dans la fenêtre WP : le gestionnaire s'exécute avec WP = 0, puis s'arrête.
3. N3 : accepté pour P4, **précondition de K1** (option B ou B′ avant toute projection non noyau).
4. Falsification conjointe de `g_meta` et `g_memmap` ; critère de la carte du démarrage non testé.
5. Monoprocesseur ; matériel réel non testé.
6. Coût (N4) : optimisation par préfiltre identifiée, non intégrée.

**Les tests réussis ne sont pas une preuve générale de sécurité. Le noyau n'est pas déclaré sécurisé**, et K0.7 n'est clôturé qu'après ta décision.
