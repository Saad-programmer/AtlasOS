## 2. Audit de l'architecture existante (i386)

### 2.1 Chemin de démarrage

Le point d'entrée C est **`kmain(uint32_t magic, uint32_t mbi_phys)`** (`kernel/core/kmain.c`). Il n'existe **pas** de `kernel_main`.

1. **Chargeur Multiboot 1** (QEMU `-kernel` ou GRUB).
   - En-tête : `kernel/arch/i386/boot/entry.asm`, section `.multiboot`. Magic `0x1BADB002`, drapeaux `PAGE_ALIGN | MEMORY_INFO` ; **pas** de bit « a.out kludge » : le chargement passe par l'ELF.
   - Image ELF32 i386 liée à **1 MiB** (`linker.ld` : `KERNEL_LOAD_ADDR = 0x00100000`, `OUTPUT_FORMAT("elf32-i386")`). [code]
   - État à l'entrée : mode protégé 32 bits, pagination désactivée, `EAX` = `0x2BADB002`, `EBX` = adresse physique de la MBI. [spec, Multiboot 0.6.96 §3.2]
2. **`_start`** (`entry.asm`) [code] :
   - `cli` ;
   - `ESP` = `boot_stack_top` ; `EFLAGS` = 0 ;
   - remise à zéro de `.bss` (`rep stosd`, `__bss_start` à `__bss_end`) ;
   - peinture de S1 (`0x5AFE57AC`) à partir de `__stack_guard_start` ;
   - arrêt si `CR0.PG` est déjà actif ;
   - canari dérivé de `RDTSC`, écrit dans `__stack_chk_guard` (`.rodata`, encore inscriptible avant la pagination) ;
   - `ESP` aligné sur 16 au moment de l'appel ; `push ebx`, `push esi` (convention **cdecl 32 bits**) ; `call kmain`.
3. **`kmain`**, dans l'ordre [code] :
   - consoles et journal ;
   - `gdt_init`, `idt_init` ;
   - `bootinfo_init` (validation du magic et copie de la MBI) ;
   - `kernel_layout_valid` ;
   - `mm_init` (carte E820, puis `pmm_init`, puis `paging_init` : **PG | WP**, puis scellement des tables) ;
   - `pic_init`, `pit_init(PIT_DEFAULT_HZ = 100)`, `keyboard_init` ;
   - en mode test, `ktest_run_all` ;
   - `paging_seal_critical` (IDT, gestionnaires, racines du VMM) ;
   - `paging_audit` (fatal en cas d'écart) ;
   - vérification des sentinelles de S2 ;
   - `idle_loop` (`sti; hlt`).

| Élément | Réalisation | Fichiers et symboles |

### 2.3 Modèle PMM et VMM [code]

| Élément | Réalisation |
|---|---|
| Carte mémoire | entrées E820 **brutes**, triées, en 64 bits (`memmap.c`) ; repli sur `mem_lower`/`mem_upper` (`mm.c`) |
| Descripteurs PMM | 16 bits par cadre : type sur 3 bits, `refs` sur 12 bits (`samos/frame.h`) ; table `g_meta[PMM_MAX_FRAMES = 2^18]` (**1 GiB**) dans `.bss` (`pmm.c`) |
| Règle de normalisation | `pmm_core_init` : les régions disponibles d'abord, puis toute autre région l'emporte |
| Distribution | `alloc_zeroed` : contrôles N1 (image, mémoire basse, carte du démarrage) et N3-I2 **avant** `memset`, remise à zéro **par l'identité** |
| Pagination | **i386 à 2 niveaux**, pages de 4 KiB ; `PTE_FRAME = 0xFFFFF000` ; `PD_INDEX`/`PT_INDEX` sur 10 bits ; **identité** de 4 KiB jusqu'à `idmap_top` ≤ `PAGING_IDMAP_LIMIT = 1 GiB` (`paging.h`, `paging.c`) |
| Protections | page nulle et gardes absentes (`va_must_stay_unmapped`) ; `.text`/`.rodata` en lecture seule ; `CR0.WP` ; structures critiques et tables scellées (P4d, P4e-2) |
| Écritures de PDE/PTE | **un seul** passage, `pt_gate_write` : validation complète, IRQ masquées, fenêtre `CR0.WP = 0` pour une seule écriture de 32 bits, WP rétabli avant IF |
| Projections dynamiques | `vmm_map`/`vmm_unmap` à `va ≥ idmap_top`, un **seul** espace d'adressage ; oracle N3 (`dyn_mapping_count`) qui parcourt les PDE ≥ `PD_INDEX(idmap_top)` |
| Audit | `paging_audit` (P4, N5, N3-I5), fatal au démarrage |

| Adresse | Rôle |

### 2.5 Hypothèses i386 explicites (à migrer)

| Hypothèse | Où | Effet en x86-64 |
|---|---|---|
| ELF32, `elf_i386`, `--target=i686-unknown-none-elf`, NASM `-f elf32` | `Makefile`, `linker.ld` | nouvelle cible et nouveau script de liaison |
| adresses sur `uint32_t`, nombreux `(uint32_t)(uintptr_t)` | `paging.c` (56 adresses ou cadres en `uint32_t`, 20 conversions), `pmm.c`, `pmm_core.c`, `gdt.c`, autotests (`test_mm.c` : 27 conversions, `test_canary.c` : 21) | troncature silencieuse au-delà de 4 GiB ; à remplacer par `uintptr_t`, `phys_addr_t` ou `uint64_t` |
| pagination à 2 niveaux, `PTE_FRAME` sur 32 bits, index de 10 bits | `paging.h`, `paging.c` | 4 niveaux, entrées de 64 bits, index de 9 bits, bit XD |
| identité physique = virtuelle (tables lues et cadres remis à zéro par l'identité) | `paging.c`, `pmm.c` (`alloc_zeroed`), `memcover` | avec un noyau *higher-half*, il faut une **projection directe** (`phys_to_virt`) |
| limite de 1 GiB, `PMM_MAX_FRAMES = 2^18` | `paging.h`, `pmm.c` | dimensionnement à revoir (table de descripteurs plus grande ou dynamique) |
| TSS 32 bits, porte de tâche #DF | `gdt.c`, `idt.c`, `exceptions.c` | **interdit** en mode 64 bits : utiliser l'**IST** |
| `pushad`, segments, `iretd`, cadre sans `SS:ESP` | `isr_stubs.asm`, `interrupt.h` | pas de `pushad` ; `iretq` ; le CPU empile toujours `SS:RSP` |
| cdecl (arguments sur la pile) | `entry.asm`, `probe.asm` | SysV AMD64 : `RDI`, `RSI`… |
| registres 32 bits en assembleur en ligne (`pushfl`, `movl %cr0`) | `arch/cpu.h` | `pushfq`, `movq` |
| trace de pile par la chaîne `EBP` | `panic.c` (`stack_collect`) | chaîne `RBP` (`-fno-omit-frame-pointer` conservé) |
| `math64` (éviter `__udivdi3`) | `lib/math64.c`, `pit.c`, `format.c` | inutile en 64 bits (division native) ; à conserver pour l'i386 |

## 3. Décision D1 — Architecture

| Critère | **A. Rester en i386** pour `kmalloc`, l'ordonnanceur, les processus et les appels système | **B. Migrer vers x86-64 avant** ces composants |
|---|---|---|
| Complexité immédiate | faible : on construit sur la base actuelle | élevée : démarrage, pagination à 4 niveaux, IST et ABI d'abord |
| Travail à refaire | **important** : cadre d'interruption, changement de contexte, convention des appels système (`int 0x80` puis `SYSCALL`), TSS (`esp0` → `rsp0`), espaces d'adressage à 2 puis 4 niveaux, chaînes de traçage : tout serait réécrit | limité au noyau K0 existant (environ 3 100 lignes dans `arch/`, plus les hypothèses de type de `paging.c` et `pmm.c`) |
| Régressions | faibles à court terme ; une seule migration plus tard, mais beaucoup plus grosse | élevées pendant la migration ; maîtrisables par sous-jalons (§7) et grâce à la référence i386 |
| Tests | inchangés à court terme | portage des bancs (QEMU, GDB, `check_elf`, mutations) ; les tests hôte sont déjà en 64 bits |
| Maintenabilité | dette croissante : chaque composant de K1 serait à reprendre | une seule cible pour K1 et la suite |
| Sécurité et isolation | **pas de NX** (i386 sans PAE) ; espace de 4 GiB partagé avec le futur espace utilisateur | NX (`EFER.NXE`, bit XD), SMEP et SMAP [spec] si le CPU les offre, IST pour #DF, NMI et #MC (R-GDT, R-NMI, R-S2), espace canonique séparant noyau et utilisateur |
| Cible i386 de référence | naturelle | **possible** : référence figée (étiquette sur `7e43b78`) ; le maintien actif d'une double cible coûte cher (bancs doublés) |

**Recommandation : B**, comme le proposait déjà la revue K0 (D1). Les composants de K1 (cadre d'interruption, changement de contexte, appels système, espaces d'adressage) sont précisément ceux qui diffèrent le plus entre i386 et x86-64. Les écrire en i386 reviendrait à les écrire deux fois, sans NX.

**Cible i386 de référence :**
- figer l'i386 comme **référence** (étiquette, par exemple `ref/i386-k0.7` sur `7e43b78`) ;
- la garder **compilable et testée en CI** tant que la parité x86-64 n'est pas atteinte (sous-jalon M64-0) ;
- puis décider de la retirer ou de la maintenir.

Ce choix revient au développeur (§10).

## 4. Décision D2 — Démarrage x86-64

### 4.1 Conditions d'entrée en mode long [spec, Intel SDM vol. 3A §9.8.5 « Initializing IA-32e Mode »]

1. Partir du mode protégé, **pagination désactivée** : c'est l'état laissé par Multiboot 1 et Multiboot 2 sur i386 [spec]. Aucun des deux ne lance le noyau en mode long.
2. `CR4.PAE = 1`.
3. `CR3` = adresse physique d'une **PML4**, dont les tables projettent au moins le code de transition en identité, plus la future adresse du noyau.
4. `IA32_EFER` (MSR `0xC0000080`) : `LME = 1`. Activer aussi `NXE` si le bit XD doit être utilisé.
5. `CR0.PG = 1` (avec `PE`) : le CPU entre en mode compatibilité (`EFER.LMA = 1`).
6. Saut lointain vers un segment de code **64 bits** (`L = 1`, `D = 0`) d'une GDT chargée au préalable.
7. Puis, en 64 bits :
   - nouvelle GDT si besoin ; **TSS 64 bits** (descripteur de 16 octets, `RSP0`, `IST1` à `IST7`) ;
   - IDT de portes de 16 octets ;
   - **plus de commutation de tâche matérielle**, donc #DF par IST ;
   - pile alignée sur 16 ; segments ignorés hormis `FS`/`GS` ; adresses **canoniques**.

`CR0.WP` reste respecté en mode long, et le mécanisme du passage (fenêtre WP) reste donc applicable [spec].

### 4.2 Faits établis par expérience (copies jetables, QEMU 8.2.2) [exp]

| Expérience | Résultat |
|---|---|
| ELF64 avec en-tête Multiboot 1, `qemu-system-{i386,x86_64} -kernel` | **refusé** : `Cannot load x86-64 image, give a 32bit one.` |
| même ELF64 converti en `elf32-i386` (`objcopy`) | **chargé**, exécution en 32 bits |
| ELF64 avec le **bit a.out kludge** (bit 16) et des adresses explicites dans l'en-tête Multiboot 1 | **chargé** (de même qu'un binaire brut) |
| en-tête Multiboot 2, `qemu -kernel` | **refusé** : `Error loading uncompressed kernel without PVH ELF Note` ; Multiboot 2 exige donc GRUB, absent de l'environnement |
| noyau i386 actuel sous `qemu-system-x86_64` | démarre ; 729 autotests réussis |

### 4.3 Comparaison

| Critère | **A. Multiboot 1 + tremplin** | **B. Multiboot 2 + tremplin** | **C. UEFI direct** |
|---|---|---|---|
| Entrée | 32 bits, sans pagination ; le tremplin fait tout le §4.1 | 32 bits, sans pagination (ou entrée 64 bits EFI via l'étiquette « EFI amd64 entry », propre à GRUB et à l'UEFI) [spec] | 64 bits, **pagination déjà active** (identité fournie par le microprogramme) [spec] |
| Format d'image | ELF64 impossible avec QEMU `-kernel` (§4.2). Deux solutions : bit a.out kludge, ou conteneur ELF32. Un noyau *higher-half* (adresse virtuelle 64 bits) se prête mal au conteneur ELF32 [hyp, à vérifier] | ELF64 accepté par GRUB [spec] | PE32+ (lld-link présent) [exp] ; chaîne de compilation nouvelle |
| Carte mémoire | MBI : `mem_lower`/`mem_upper`, carte E820 (code et tests existants) | étiquettes MB2 (carte E820 ou EFI, RSDP ACPI, tampon d'image) | `GetMemoryMap`, puis `ExitBootServices` avec la clé courante [spec] ; nouveau code |
| QEMU `-kernel` (bancs automatiques) | **oui** (§4.2) | **non** : il faut GRUB et une ISO (`grub-mkrescue`, `xorriso` absents) | non : OVMF et une partition FAT d'amorçage |
| GRUB et matériel réel | GRUB accepte Multiboot 1 [spec] | GRUB accepte Multiboot 2 [spec] | natif sur machine UEFI |
| Continuité avec l'existant | **maximale** : `bootinfo`, `memmap`, 86 cas QEMU | moyenne | faible |
| Hypothèses d'identité | le tremplin crée son identité ; il faut les **retirer** ensuite si l'on veut un noyau *higher-half* | idem | l'identité du microprogramme doit être **remplacée** par nos tables |
| Dépendances nouvelles | aucune | GRUB, `xorriso` (outils hôte) | OVMF (présent), `lld-link`, image FAT (`mtools` absent) |

**Recommandation : A** (Multiboot 1 + tremplin 32 → 64 bits), avec la décision de **format d'image** prise sur expérience dans le sous-jalon M64-2 :
- **bit a.out kludge**, vérifié ;
- **ou** petit chargeur 32 bits qui embarque le noyau 64 bits.

Raisons : continuité des 86 cas QEMU et du banc de mutations ; aucune nouvelle dépendance ; contrôle complet de la transition.

**C (UEFI)** est à prévoir dans une phase dédiée, pour le matériel réel (D4). **B** n'est à retenir que si GRUB devient une dépendance acceptée.

## 5. Décision D4 — Validation matérielle

| Étape | Contenu | Nature |
|---|---|---|
| 1 | `qemu-system-x86_64`, démarrage BIOS (SeaBIOS), Multiboot 1. **Déjà possible pour la référence i386** (729 autotests réussis, §4.2) | émulation |
| 2 | configurations de RAM (16 MiB à 4 GiB et au-delà), modèles de CPU (`-cpu` avec ou sans `nx`, `pdpe1gb`, ou sans `lm` pour tester le refus), sous TCG | émulation |
| 3 | OVMF/UEFI **seulement si** la stratégie C est retenue pour le matériel réel ; en attendant, OVMF peut servir à tester un démarrage par GRUB s'il est adopté | émulation |
| 4 | matériel réel (EliteBook UEFI), **après une revue de sûreté dédiée** : démarrage depuis un support amovible, **aucune écriture sur les disques physiques** (aucun pilote de stockage en écriture, vérification par relecture du code et par test), journal par port série ou à l'écran | **validation matérielle** |

**Aucune étape d'émulation ne vaut validation matérielle.** Les mesures de coût et les comportements du TLB, des NMI et du microcode ne se transposent pas.

## 6. Matrice des invariants (rien n'est acquis en x86-64 avant validation)

| Invariant i386 actuel | Équivalent x86-64 attendu | Vérification prévue | Risque de régression |
|---|---|---|---|
| page nulle non projetée (E1) | page 0 absente dans la PML4 du noyau ; aucune identité basse après le tremplin | sonde de lecture et d'écriture à 0 ; `info tlb` ou `info mem` ; mutation | identité du tremplin oubliée (la page 0 resterait projetée) |
| pages de garde S1 et S2 | gardes non présentes autour de chaque pile, **piles IST** comprises | dépassement provoqué, puis #DF sur l'IST ; mutation | l'IST masque le débordement, ou une garde manque |
| `.text`/`.rodata` RO, `CR0.WP` | RO avec `WP` ; **NX** sur données et piles (`EFER.NXE`, bit XD) | écriture dans `.text` (#PF) ; exécution en `.data` (#PF avec I/D = 1) ; `check_elf` (pas de W+X) | XD non activé (`NXE` oublié), ou W et X à la fois |
| image non projetable ailleurs (D1) | idem ; critères indépendants du PMM (symboles de liaison) | mode `pmmtrust` porté ; mutations | adresses virtuelles et physiques confondues (*higher-half*) |
| métadonnées PMM, N1 | idem, avec des adresses physiques sur 64 bits | tests hôte (déjà en 64 bits) ; `imageint` porté | troncature de type `(uint32_t)` |
| `refs` et oracle N3 | oracle sur **4 niveaux** (PML4 → PT), ou comptes scellés (approche B) : **décision** | mode `n3` porté ; mutations des bornes (dernière entrée de chaque niveau) | parcours incomplet d'un niveau ; coût |
| tables scellées (P4e-2), PDE à écriture unique (D3) | toutes les tables (PML4, PDPT, PD, PT) scellées ; écriture unique par niveau | `paging_audit` 64 bits ; modes `seal*` | nouveaux niveaux non couverts par le passage |
| fenêtre d'écriture privilégiée (passage, CR0.WP) | même mécanisme (WP respecté en mode long) ou projection temporaire par CPU : **décision** | `check_elf` (règles CR0 et INVLPG en registres 64 bits) | règles de code machine non portées : faux PASS |
| INVLPG (D2) | `invlpg` en 64 bits ; vidage sélectif | `check_elf` ; harnais `tlb_integration` porté | QEMU masque toujours les oublis |
| exceptions, #DF | portes de 16 octets ; **#DF, NMI, #MC sur IST** (et non porte de tâche) ; sentinelles sur les piles IST | modes de faute portés ; #DF réel ; NMI injectée par GDB | NMI pendant la fenêtre WP ; pile IST corrompue par réentrance |
| fail-stop, audits indépendants | `paging_audit` et sentinelles au démarrage, panique sur écart | cas QEMU négatifs ; mutations | audit partiel sur 4 niveaux |
| refus d'un CPU inapte | **nouveau** : refus explicite sans mode long, PAE ou NX (`CPUID`), avant toute bascule | `-cpu` sans `lm` : diagnostic et arrêt, sans triple fault | triple fault silencieux |

## 8. Inconnues techniques

1. **Format de l'image 64 bits** avec QEMU `-kernel` : bit a.out kludge (vérifié), chargeur 32 bits embarqué, ou conteneur ELF32. Compatibilité avec un noyau *higher-half* (`-mcmodel=kernel`, `0xFFFFFFFF80000000`). [hyp]
2. **Disposition virtuelle :** identité temporaire puis *higher-half* et projection directe, ou identité conservée au début. Effet sur toutes les preuves P4 qui reposent sur « physique = virtuelle ».
3. **Dimension du PMM** au-delà de 1 GiB : table statique ou dynamique, et coût en mémoire.
4. **N3 sur 4 niveaux :** coût d'un parcours complet ; comptes scellés (approche B) ou projection inverse.
5. **Fenêtre CR0.WP en 64 bits** face aux NMI et #MC, désormais sur IST : la fenêtre reste-t-elle acceptable, ou faut-il une projection temporaire par CPU ?
6. **Fonctions disponibles sous QEMU TCG** (NX, SMEP, SMAP, `pdpe1gb`, LA57) : à mesurer par `CPUID` sur les modèles `-cpu` utilisés.
7. **Interactions de l'ABI :** zone rouge, SSE dans le noyau, alignement de pile dans les stubs, `-mgeneral-regs-only` en 64 bits.
8. **Portage des bancs de code machine** (`check_elf`, `tlb_integration`, mutations) sans perte de pouvoir de détection.

## 9. Risques et contre-mesures

| Risque | Contre-mesure |
|---|---|
| migration monolithique, régressions invisibles | sous-jalons M64-0 à 9 ; référence i386 testée en CI jusqu'à la parité |
| faux PASS en 64 bits (règles de code machine non portées) | porter chaque règle de `check_elf` **avec** sa mutation de contrôle avant de s'y fier |
| triple fault sans diagnostic pendant la bascule | messages debugcon à chaque étape du tremplin ; GDB ; contrôles `CPUID` avant toute bascule |
| perte d'une garantie P4 ou N3 | matrice du §6 ; audit contradictoire dédié après M64-7 et M64-8 |
| dépendances nouvelles (GRUB, outils UEFI) | D2 = A (aucune) ; UEFI dans une phase dédiée |
| écriture sur un disque réel | aucun pilote de stockage en écriture ; revue de sûreté avant tout essai matériel |
| dette double cible | décision explicite à M64-9 |
