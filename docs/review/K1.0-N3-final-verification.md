## 2. Vérification critique de U2

### 2.1 Code examiné (`kernel/arch/i386/paging.c`, `vmm_unmap`)

```c
if (va < g_idmap_top) return SAMOS_EPERM;              /* identité : jamais retirée */
uint32_t *pt = get_table(va);                          /* g_pd[PD_INDEX(va)] */
if (pt == 0 || !(pt[PT_INDEX(va)] & PTE_PRESENT)) return SAMOS_ENOENT;
uint32_t frame = pt[PT_INDEX(va)] & PTE_FRAME;
uint32_t real = dyn_mapping_count(frame, 0u);          /* (1) AVANT l'effacement */
bool release_ref = type(frame) == FRAME_ALLOCATED && pmm_refs(frame) >= real && real != 0;
ge = pt_gate_write(PT_KIND_PTE, va, 0);                /* (2) PTE := 0 */
if (ge != SAMOS_OK) return ge;                         /*     refus : rien n'a changé */
cpu_invlpg(va);                                        /* (3) */
if (release_ref) { e = pmm_unref(frame); KASSERT(e == SAMOS_OK); }   /* (4) */
else g_unmap_ref_anomalies++;
```

- **D est relevé avant l'effacement**, et la PTE retirée y figure. En effet, `va ≥ g_idmap_top` (sinon EPERM). `dyn_mapping_count` parcourt `g_pd` depuis `PD_INDEX(g_idmap_top) ≤ PD_INDEX(va)` et retient chaque PTE présente à `va' ≥ g_idmap_top`. `get_table` lit le même `g_pd`. Donc `D ≥ 1`, et la condition `real != 0` est redondante (défensive).
- **Entre (1) et (4), `g_meta` n'est pas modifiée.** `pt_gate_write` et `pt_gate_check` lisent le type PMM mais n'écrivent que la PTE. Aucun gestionnaire d'interruption n'alloue, ne libère, ne projette ni ne retire de projection (hypothèse monoprocesseur, R-SMP).
- **`pmm_unref` ne peut pas échouer** dans la branche (4) : le type est ALLOCATED et `refs ≥ D ≥ 1`. `KASSERT` reste actif dans l'image de production (`panic.h` : `panic` inconditionnel).
- **Refus du passage en (2) :** retour sans aucun effet (PTE, TLB et références intacts).

### 2.3 Preuve : aucune projection restante ne perd sa référence

**Énoncé.** Soit un retrait qui réussit. Les projections restantes du cadre sont au nombre de `D - 1`. Alors :

$$r' \;\ge\; \min(r,\; D - 1)$$

Autrement dit, si les références couvraient les projections restantes avant le retrait (`r ≥ D - 1`), elles les couvrent encore après.

**Démonstration.**
- **Cas 1 :** `release_ref` est vrai. Le type est ALLOCATED et `r ≥ D`, donc `r' = r - 1 ≥ D - 1`.
- **Cas 2 :** `release_ref` est faux. Aucune écriture dans `g_meta`, donc `r' = r ≥ min(r, D - 1)`.

Dans les deux cas, le retrait ne fait jamais passer `refs` sous `D - 1` lorsque `refs` était au moins égal à `D - 1`. Si `refs` était déjà inférieur, il reste inchangé et le déficit ne s'aggrave pas. **∎**

**Ce que la preuve ne dit pas.**
- Un compteur unique ne distingue pas les références de projection des références prises pour d'autres raisons (épinglage par `pmm_ref`). Si `refs` est falsifié vers le bas sur un cadre à la fois projeté et épinglé, les retraits peuvent consommer la part « épinglage ». Une fois toutes les projections retirées, le cadre peut alors être libéré malgré l'épinglage.
- Aucun code de production n'épingle de cadre aujourd'hui (seuls les autotests appellent `pmm_ref`). C'est une **limite**, pas un défaut de U2 : un épinglage futur devra disposer d'une source indépendante.
- **Sûreté de la libération :** elle ne repose pas sur cette propriété. `pmm_free_frame` et `alloc_zeroed` consultent l'oracle, donc un cadre projeté reste protégé même si `refs` vaut 0.

### 2.4 Ordre exact

- Sur le code machine de l'image de production, `check_elf.sh` vérifie la règle `vmm_unmap pmm_unref` :
  - exactement un `invlpg` ;
  - placé après le dernier `call pt_gate_write` ;
  - dont l'opérande est l'argument `va` du passage ;
  - et suivi de `call pmm_unref`.
  Elle passe sur `04c08f7` (31 vérifications en production, 0 échec, §8).
- Une sonde qui place `pmm_unref` **avant** l'`invlpg` (X3, §5.3) n'est vue par **aucun** test de comportement, puisque la fenêtre CR0.WP vide tout le TLB sous QEMU. Elle est détectée par `check_elf.sh` (`vmm_unmap:invlpg:2`, le compilateur ayant dupliqué l'instruction). La preuve de l'ordre repose donc sur l'**analyse du code machine**, comme pour D2 en P4f-B4.

| Mode | Contenu du cadre au refus | `g_meta[x]` | `free_count` | PDE de `0xCC000000` | `g_tables` |
|---|---|---|---|---|---|

**Lecture :**
- **Avant `memset` :** oui pour R2 et R6. La première couche (PMM) arrête le noyau sur un cadre intact.
- **Avant la réattribution :** oui. `alloc_zeroed` ne rend jamais le cadre, puisque la panique est sans retour.
- **Publication d'une table interdite :** aucune PDE n'est publiée et `g_tables` est inchangé.
- **Références :** aucune référence de projection n'est modifiée.
- **Constat LOW :** au moment du refus, `pmm_core_alloc_as` a **déjà** réécrit le descripteur falsifié (FREE → ALLOCATED ou PAGETABLE, `refs = 0`, `free_count − 1`, `hint`). Si ce refus devenait un jour récupérable (une erreur au lieu d'une panique), il faudrait restaurer le descripteur.
- **Seconde couche (`tablealias_l2`) :** le contrôle D1 de `table_create` n'empêche **pas** la destruction (le cadre est déjà remis à zéro). Il empêche le **scellement et la publication** : aucune PDE, et l'identité du cadre reste `0x…063`, inscriptible, donc non scellée. C'est voulu. Seule la première couche protège les données, et ce mode ne sert qu'à éprouver la seconde.

## 6. Performance

**Montage :** mode jetable `n3bench` (annexe du rapport d'implémentation), identique dans une copie de `a7a6e2c` et dans une copie de `04c08f7`. TCG, ×1024 cycles, 1 000 opérations, minimum et maximum.

| RAM | Tables dynamiques | `alloc` + `free`, base | K1.0 | facteur (min/min) | `alloc` + `map` + `unmap` + `free`, base | K1.0 |
|---|---|---|---|---|---|---|
| 128 MiB | 0 | 24,4-29,7 M | 64,2-74,8 M | ×2,6 | — | — |
| 128 MiB | 1 | 23,1-25,1 M | 80,5-140,4 M | ×3,5 | 58,8-82,8 M | 155,8-167,9 M |
| 128 MiB | 8 | 22,3-25,9 M | 182,3-207,6 M | ×8,2 | 58,2-69,0 M | 311,8-367,1 M |
| 128 MiB | 32 | 23,6-28,8 M | 549,5-605,8 M | ×23 | 58,6-64,2 M | 982,0-1299,0 M |
| 1500 MiB (gestion plafonnée à 1 GiB, `idmap_top` aligné) | 0 | 23,3-24,1 M | 47,6-74,5 M | ×2,0 | — | — |
| 1500 MiB | 32 | 24,3-24,5 M | 503,7-523,3 M | ×21 | 57,7-58,5 M | 952,0-1061,1 M |

Les mesures du rapport d'implémentation sont reproduites (×2,7, ×6,7 et ×22,7 alors ; ×2,6, ×8,2 et ×23 ici), avec un bruit de TCG notable, jusqu'à ×1,7 entre deux mesures.

**Coût fixe, corrigé.** Le rapport d'implémentation (§6) attribuait le coût sans table dynamique à la seule table de la frontière. **C'est incomplet.**
- À 1500 MiB, sans table de frontière, le coût reste d'environ ×2 : chaque appel à l'oracle lit les 768 PDE au-delà de `idmap_top`, et il y a deux appels par couple.
- À 128 MiB, il lit 993 PDE **plus** les 1 024 PTE de la table de la frontière, dont 992 PTE d'identité inutiles, ce qui ajoute environ 16 M (≈ 8 000 cycles TCG par couple).
- Une table dynamique supplémentaire coûte environ 15 M par 1 000 couples (≈ 7 500 cycles par appel).

**Conséquences pour les allocations futures :**
- `pmm_alloc_frame` et `pmm_free_frame` coûtent désormais O(PDE au-delà de l'identité + 1 024 × tables dynamiques), contre O(1) amorti auparavant (hors `memset`). `vmm_unmap` ajoute un relevé complet.
- Un `kmalloc` (K1.2) alimenté page par page paiera ce coût à chaque page.
- Avec plusieurs espaces d'adressage (K1.4), le nombre de tables croît avec le nombre de processus. L'approche A devient alors prohibitive, et en x86-64 (4 niveaux, 512 entrées) le parcours est encore plus large. Il faudra réexaminer l'approche B, ou une projection inverse scellée, **avant** K1.4 ; ce sera une décision d'architecture.
- Sur matériel réel : **NON MESURÉ**. Aucune optimisation n'a été faite pendant cette revue.

## 10. Décision

**B — Une correction ciblée est encore nécessaire.**

Le mécanisme est **correct** :
- U2 est prouvé (§2.3) ;
- l'ordre est vérifié sur le code machine ;
- aucune erreur de frontière n'a été trouvée dans le code ;
- les refus interviennent avant la destruction ;
- les 13 mutations sont distinctes et directes.

**Une révision architecturale (C) n'est pas nécessaire pour le modèle actuel.** Elle le deviendra avant K1.4, ce qui est déjà consigné.

**En revanche, deux bornes de l'oracle, la dernière PTE d'une table et la dernière PDE, ne sont protégées par aucun test** (sondes X9 et X10 non détectées). La correction proposée ne touche **que les tests**, pas le code de production :
1. mode `n3` : projections à l'index 1023 d'une table (par exemple `0xD13FF000`) et dans la dernière PDE (`0xFFFFF000`), avec des assertions nommées (comptage, libération refusée, retraits) ;
2. mode `n3` : un cadre à 3 alias en déficit, avec l'assertion `ref_mismatch == 1` (déduplication, X4) ;
3. mutations versionnées : X9, X10, X4 ; et, pour la durabilité, X1, X2 et X3, cette dernière par `mutant_tool` sur `check_elf.sh` ;
4. correction de l'explication du coût fixe dans `docs/review/K1.0-N3-implementation.md` §6 (§6 ci-dessus).

Si cette correction est faite et validée par les bancs complets, je recommanderais alors la décision **A**. Sans elle, l'intégration resterait techniquement possible, puisque le code est correct, mais avec une protection contre les régressions incomplète sur ces bornes.

**Aucune modification n'a été faite. K1.1 et la migration x86-64 ne sont pas commencés. K0.7 n'est pas clôturé.**

### 11.2 Dernière PDE : contraintes vérifiées

Aucune réservation de la PDE 1023 dans ce noyau :
- aucune projection récursive (relecture de `paging.c` : aucune référence à cette PDE) ;
- aucun MMIO projeté ;
- les adresses **physiques** hautes (APIC `0xFEE00000`, ROM `0xFFFE0000`) ne concernent pas l'espace **virtuel**.

Le scénario vérifie avant la projection que la PDE est absente, puis :
- `va ≥ idmap_top` et `va >> 22 == 1023` ;
- la PDE publiée vaut P | W, plus éventuellement A (`0x0173c023`), et l'audit l'accepte ;
- la table est **scellée** (identité sans W), n'est pas projetée dynamiquement, et l'audit reste propre.

`0xFFFFF000`, la dernière page de l'espace, n'est **pas** utilisée par le banc versionné, ce qui évite toute arithmétique `va + 4 KiB` qui déborderait. Elle a été vérifiée séparément dans la copie jetable B2 (§3).

**Contrainte à conserver :** si une version future réserve la PDE 1023 (projection récursive, MMIO), ce scénario devra viser la **dernière PDE parcourue** par l'oracle, et non la PDE 1023 en dur.
