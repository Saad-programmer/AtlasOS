# K0.7-P4f-B4 — Preuves de cohérence du TLB et des invalidations INVLPG (correction de D2)

**Périmètre :** défaut D2 de l'audit P4f-A, une régression de **couverture**. Le code exécutait bien ses INVLPG ; c'est la preuve qui avait disparu. P4f-C et K1 ne sont pas traités, et le VMM n'est pas refondu.
**Base :** commit `b1cf4eaf` (P4f-B3) ; `main` = `95b9cb5` ; aucune PR ; stash existant intact.

## 1. Cause de D2

Depuis P4e-1, chaque écriture de PTE du VMM passe par la fenêtre CR0.WP de `pt_gate_write` (WP = 0, une écriture, WP = 1).
- **Sous QEMU (TCG) :** tout changement de CR0.WP vide le TLB entier (`cpu_x86_update_cr0`). Chaque modification de PTE est donc suivie d'un vidage complet, et un INVLPG oublié n'a plus d'effet observable.
- **Sur un processeur réel :** MOV vers CR0 n'invalide le TLB que si PG passe de 1 à 0 (SDM vol. 3A §4.10.4.1). Un INVLPG oublié y laisse une traduction périmée.

Le test K0.6 (`test_mm.c`) qui prouvait l'INVLPG de `vmm_unmap` (« la lecture suivante réussirait encore ») est ainsi devenu aveugle **sans changer**. Le commentaire « vérifié par autotest » de `vmm_unmap` était donc inexact.

### Reproduction (copie isolée, `b1cf4eaf` + modifications de B4)

| INVLPG supprimé | Passage réel (vidage par CR0.WP) | Copie sans écriture de CR0 |
|---|---|---|
| `vmm_unmap` | `test` : 727 vérifications, **0 échec** ; `test=tlbvmm` : 0 échec | `test=tlbvmm` : **2 échecs** (`unmap_translation_removed`, `second_unmap_removed`) |
| `map_page` | `test` : 0 échec ; `test=tlbvmm` : 0 échec | `test=tlbvmm` : **0 échec** |

**Conclusion :** le masquage par CR0.WP est **confirmé** pour `vmm_unmap`. Pour `map_page`, le retrait est invisible **même sans vidage implicite** : c'est attendu, car cette invalidation est architecturalement optionnelle (§2). Un retrait non détecté ne prouve pas qu'une instruction est inutile ; seule l'analyse architecturale le tranche.

## 4. Audit du code machine

Les quatre fonctions sont `SAMOS_NOINLINE` depuis B4 (`map_page`, `vmm_unmap`, `paging_seal_identity` ; `seal_table_frame` l'était déjà), donc une seule copie de chacune existe. Relevé manuel (image de production) :

| Fonction | Argument `va` du passage (`%edx`) | INVLPG | Ordre |
|---|---|---|---|
| `vmm_unmap` | `mov %esi,%edx` (`%esi` ← `0x8(%ebp)` = va) | `invlpg (%esi)` | `call pt_gate_write` < `invlpg` < `call pmm_unref` |
| `map_page` | `mov -0x1c(%ebp),%edx` | `mov -0x1c(%ebp),%ecx ; invlpg (%ecx)` (même case) | après le passage |
| `paging_seal_identity` | `mov %ebx,%edx` | `invlpg (%ebx)` | après le passage, dans la boucle |
| `seal_table_frame` | `mov %edi,%edx` | `invlpg (%edi)` | après le passage |

**Assembleur inline :**
- `cpu_invlpg` = `asm volatile("invlpg (%0)" : : "r"(vaddr) : "memory")` : l'opérande est une adresse en registre, donc une forme mémoire correcte d'INVLPG ;
- le clobber `memory` empêche le compilateur de déplacer une lecture ou une écriture mémoire au-delà de l'instruction ;
- `pt_gate_write` (fonction externe à l'appelant, `cpu_write_cr0` avec clobber `memory`) est appelé avant ;
- le code machine confirme l'ordre dans les quatre fonctions.

**Compatibilité avec WP :** INVLPG ne lit ni n'écrit la page invalidée. Il n'est soumis ni aux droits de la page ni à CR0.WP, et il s'exécute hors de la fenêtre.

**Règle `check_elf.sh`** (deux images), pour chacune des quatre fonctions :
1. **exactement un** `invlpg` : une invalidation étrangère supplémentaire ne peut pas satisfaire la règle ;
2. situé **après** le dernier `call <pt_gate_write>` qui le précède ;
3. **opérande** égal à l'adresse passée au passage : soit `mov %R,%edx` avant l'appel sans réécriture de `%R`, soit `%R` rechargé depuis la même case mémoire que `%edx`, non réécrite entre-temps ;
4. pour `vmm_unmap`, **avant** `call <pmm_unref>`.

Diagnostics :
- `F:absente` ;
- `F:sans-invlpg` ;
- `F:invlpg:N` ;
- `F:sans-appel-pt_gate_write` ;
- `F:operande` ;
- `F:invlpg-apres-pmm_unref`.

La mutation M55 vérifie le contrôle d'opérande : un INVLPG sur `va + 0x1000` donne `vmm_unmap:operande`.

**Limites :** l'analyse suit l'ordre du listing, pas tous les chemins de contrôle. Elle dépend des conventions d'appel internes choisies par Clang (`%edx` pour `va` dans l'appel statique de `pt_gate_write`) ; un changement de compilateur peut exiger d'adapter la règle, et elle échouerait alors bruyamment. La règle « avant `pmm_unref` » n'est pas couverte par une mutation : un déplacement d'instruction ne se réduit pas à une substitution de texte unique.

## 5. Expériences comportementales

### 5.1 Isolée : `test=tlbexp` (18 vérifications)

**Mise en place :**
- `va = 0xC8000000` → cadre A, dans une table T scellée ;
- un **alias inscriptible temporaire** de T est écrit à `0xC8401000` par le prototype de test P4c, qui a sa propre fenêtre WP. Celle-ci vide le TLB **avant** l'expérience.

**Pendant l'expérience : aucune écriture de CR0 et aucune fenêtre du passage** (`cr0_untouched` : CR0 et compteur de fenêtres inchangés, WP actif).

| Étape | Sans INVLPG | Après `invlpg va` |
|---|---|---|
| changement de cadre A → B (après lecture de va) | `stale_after_frame_change` : la lecture rend **A** | `new_frame_after_invlpg` : la lecture rend **B** |
| retrait (présent → absent) | `stale_after_unmap` : la lecture **réussit** (B) | `fault_after_unmap_invlpg` : faute, CR2 = va, code 0 |
| retrait de W (WP actif) | `stale_write_after_ro` : l'écriture **réussit** | `write_faults_after_invlpg` : faute, CR2 = va, code 3 |

**Remise en état :**
- PTE d'origine rétablie, puis INVLPG ;
- alias retiré par le prototype : la lecture par l'alias faute ;
- projections retirées et cadres rendus ;
- audit propre (aucun alias, aucune structure inscriptible), PMM cohérent, WP actif.

**Mutation M58 :** sans l'INVLPG de l'étape 1, `new_frame_after_invlpg` échoue. L'expérience détecte donc bien l'absence d'invalidation.

**Nature de l'alias :** il est écrit **hors** du passage, dans le mode isolé seulement. Il n'existe que pendant l'expérience, est retiré avant la fin, et sa présence ou son absence est vérifiée par l'audit. L'image de production ne contient ni ce mode ni le prototype (`TEST_ONLY_SYMS`). Aucun passage privilégié n'a été ajouté.

**Observation propre à QEMU :** une traduction périmée **peut** survivre, mais rien ne garantit qu'elle survive sur un processeur réel (éviction du TLB). Les assertions « sans INVLPG » décrivent QEMU, et servent à montrer que l'expérience est sensible.

## 7. Hypothèses architecturales

1. Une entrée P = 0 n'est jamais mise en cache, ni dans le TLB ni dans les caches des structures de pagination (SDM vol. 3A §4.10.2.3, §4.10.3.1, §4.10.4.3).
2. INVLPG invalide les entrées du TLB **et** des caches des structures pour l'adresse donnée (§4.10.4.1).
3. MOV vers CR0 n'invalide le TLB que si PG passe de 1 à 0 (§4.10.4.1). **QEMU, lui, vide tout le TLB à chaque changement de PG, WP ou PE.**
4. Aucune entrée n'est globale (bit G jamais posé ; CR4.PGE = 0), donc l'écriture de CR3 invalide tout.
5. Monoprocesseur : un INVLPG local suffit. En SMP, il faudrait un *shootdown* entre processeurs.

## 8. Garanties démontrées et garanties non testées

**Démontrées :**
- Sous QEMU, INVLPG retire une traduction périmée pour un changement de cadre, un retrait et un retrait de W, sans aucune écriture de CR0.
- Le VMM réel retire ses traductions par `vmm_unmap` sans dépendre d'un vidage implicite (intégration, avec contrôle de sensibilité).
- Les quatre INVLPG existent dans le code machine des deux images, sur la bonne adresse, après l'écriture et, pour `vmm_unmap`, avant `pmm_unref`.
- La disparition de chaque INVLPG est détectée (M53-M58, M31).

**Non testées :**
- Le comportement sur processeur **physique**, ou sous KVM : persistance réelle des traductions, effet réel d'INVLPG, absence de vidage par CR0.WP. **NOT TESTED.**
- L'effet comportemental des INVLPG de scellement dans le VMM réel (preuve structurelle seulement).
- L'ordre « INVLPG avant `pmm_unref` » sous mutation (contrôle structurel présent, pas de mutation).
- Le multiprocesseur.
